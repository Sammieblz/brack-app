# Overlay, date and form coverage reconciliation

Source review: 2026-09-28, current commit `db076cf` (F09 committed). This review changes documentation only. It does not claim new browser, device, screen-reader or persistence test results.

The original F08 ticket promised a shared adaptive overlay/form/date contract. The implementation establishes a useful boundary and migrates a named subset, but it does **not** establish that contract across the application's actual tasks. The checkpoint's qualification “for the listed F08 scope” is accurate; treating it as closure of the original cross-application requirement is not. Several omitted tasks contain the same responsive-owner problem that was fixed for Dashboard Goals. Those omissions need explicit corrective work before further screen polish is presented as completing the shared foundation.

## Continuation status

This report records the `db076cf` source baseline. [CR01/checkpoint21](../21-live-composers.md) repairs OF-03's direct/club media names, descriptions, load failures and exact focus return, with actual GIF/emoji/media layering and Close/Escape/app-Back evidence. This is a semantics/lifecycle repair using the existing primitive, not a universal AdaptiveDialog migration. Other geometry, responsive ownership and form/confirmation rows retain their assigned corrective batches.

## Method and evidence limits

Read the delivery, frontend UX and Graphify skills; design-system specification 04, screen/state specification 05, accessibility specification 07, execution ticket F08 in 09, checkpoint 18, `ui-adaptive-overlays.md` and the F08 action/Goals evidence. Queried the existing local graph with `AdaptiveDialog ActionSheet Dialog DatePicker ProfileDrawer FullScreenLoading OverlayBackBoundary --budget 2200`: 9,250 indexed nodes; 370 matched, 66 returned. The truncation required source searches rather than assuming the returned neighborhood was complete. Read generated Obsidian notes for AdaptiveDialogContent, GoalManager, CreatePostDialog, SyncReviewDialog and DatePicker, then verified their source links.

Source enumeration covered client production TSX imports and rendered Dialog/AlertDialog/Sheet/Drawer/Popover/ActionSheet/AdaptiveDialog/DatePicker/TimePicker usages; custom Radix roots, portals, browser confirmations; and enclosing screen ownership. A broader `apps`/`packages` search found the renderer-owned custom modal roots in `apps/client`; shell/data portals are distinguished from modal tasks below. Direct-import absence does not prove an arbitrary dynamic loader cannot exist; the dormant classification means no current static production incoming consumer was found.

Evidence labels used here:

- **Migrated**: current source uses the F08 adaptive boundary, directly or through a wrapper. This does not prove its feature guards or all parents are correct.
- **Inherited**: current source receives shared Radix semantics and F07 Back-layer registration, but retains its previous geometry and feature owner.
- **Recorded fixture**: an earlier checkpoint records a relevant passed test. This review did not rerun it. A synthetic fixture cannot establish physical IME, real AT, OS camera return or native tablet behavior.
- **Source defect**: the current implementation directly demonstrates the missing name, unconditional draft reset, replacement owner or absent pending gate. Geometry problems described as risks require the specified actual-consumer reproduction; no overflow measurement is fabricated.

## Corrections to completion language and the next handoff

1. Retain the successful F08 primitive/date/journal work and its exact recorded evidence. Do not relabel it a total failure or claim its tests exercised these omitted consumers.
2. Describe F08 as **adaptive foundation and enumerated migrations**, with OF-01–OF-07 carried as explicit unmet cross-application requirements. The original 04/05/07 requirements did not waive dirty substantial forms, actual parent retention, meaningful modal names or keyboard usability because visual screen tickets came later.
3. F10–F18 still own intentional whole-screen hierarchy, grouping, density, typography and feature-specific content. Merely changing Dialog imports cannot satisfy those requirements. Conversely, postponing a proven draft-loss or unnamed-modal issue until visual polish is not justified by ticket sequence.
4. Date coverage must state which tests use a real picker, which mock it, and which actual enclosing page is mounted. Apply the same rule to shell/Back/editor fixtures. Source migration, browser behavior, whole-screen visual review, physical native acceptance and AT acceptance are separate ledger columns.
5. Before the next implementation, select a bounded corrective unit from this matrix, list all affected consumer entries and mutations, run Playwright after the unit, inspect the actual screen captures, update the coverage record, and stop for the user's review. This document authorizes no code changes or commits by itself.
